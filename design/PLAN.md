## Branch and deploy

- **Work happens on `rebuild/cinematic`, not `master`.** The live site is today served by GitHub Pages straight from `master`'s root `index.html`. Pushing a Next.js project to `master` would break it before the new one deploys.
- **At phase 7:**
  1. Merge into `master`.
  2. Switch **Settings → Pages → Source** to _GitHub Actions_. **Gabriel does this step, and the build tells him exactly when, before the merge.**
  3. `deploy.yml` then publishes `out/`.
- **The old site:** `index.html`, `static/js` and `static/icons` are deleted in phase 0.
  - `static/img/bookowl.png` moves to `public/scenes/` as the source for its AVIF/WebP.
  - `static/img/pianosoparabaixinhos.png` is out of scope (agreed), so it is not used. It stays in git history only.

## Content schema (additions)

```ts
type Todo = { todo: string } // todo('what is missing'): marks a gap
type Text = string | Todo

type BehindTheScenes = {
  problem: Text
  role: Text
  architecture: {
    nodes: {
      id: string
      label: string
      kind: 'client' | 'service' | 'data' | 'external' | 'device'
    }[]
    edges: { from: string; to: string; label?: string }[]
  }
  decisions: { what: Text; why: Text }[] // 2–3 entries
  testingAndDeploy: Text
  outcome: Text
  links: { label: string; href: string }[] | { internal: true }
}
```

- **`Todo` values in development:** they render as a clearly marked dashed placeholder reading "TODO(gabriel): …".
- **`Todo` values in the production build:** they are omitted. Their sub-heading is hidden too, so nothing unfinished reaches the live site. Each omitted value is listed as a build warning and in `pnpm todos`.
- **Tests:**
  - A schema test fails if `decisions` has fewer than 2 or more than 3 entries.
  - A content test fails if an internal project has links or a non-fictional still.

## LCP measurement

`pnpm measure:vitals` loads the page on a 390 px phone with Slow 4G (150 ms latency, 1.6 Mbps) and a 4× CPU slowdown, five times with the cold open and five without, in each locale (from phase 6; `LOCALE=es` for one). It prints the median and the range of the runs.

- **Gzip, from phase 4.** `pnpm preview` now gzips text the way GitHub Pages does. Before, the HTML arrived uncompressed and competed with the render-blocking CSS for the throttled bandwidth. When Act II grew the HTML from 64 KB to 177 KB raw, some runs reached 3–4 s although the gzipped page is 27 KB. Numbers before phase 4 (1.33 s and 1.94 s in phase 2, 1.52 s in phase 3) come from that uncompressed setup.
- **After the cleanup, per locale:** PT 0.62 s, EN 0.62 s, ES 0.62 s; CLS 0.002 or less. There is no cold open to measure with and without any more.
- **Phase 7, per locale** (without / with the cold open): PT 0.66 / 0.66 s, EN 0.66 / 0.66 s, ES 0.65 / 0.66 s; CLS 0.002 or less. Every run now lands between 0.64 and 0.67 s: the slow runs near 1.07 s were the hero waiting on bandwidth shared with the unused `latin-ext` fonts.
- **Phase 6, per locale** (without / with the cold open): PT 0.71 / 0.71 s, EN 0.70 / 0.71 s, ES 0.71 / 0.71 s; CLS 0.003 or less everywhere. The Spanish hero first measured **CLS 0.234**: its relocation line set in two lines in the fallback font and one in Newsreader, so the swap moved the whole centred hero. Fixed by capping that line at 30ch on phones and top-aligning the hero there (see STORYBOARD §1).
- **Phase 5:** LCP 0.69 s (range 0.68–1.10 s), 0.70 s with the cold open; CLS 0.002.
- **Phase 4, same machine, gzip:**
  - phase 3 build: LCP 0.65 s (range 0.64–0.90 s)
  - phase 4 build: LCP 0.70 s (range 0.67–1.04 s)
  - CLS 0.002 in both
- **About 110 KB of the 177 KB HTML is Next's RSC payload**, which repeats the server tree. It compresses well, but it is the first thing to look at if the page grows again. Next in line are the inline mockups (33 KB raw).

## Lighthouse (phase 7)

`pnpm lighthouse` runs three configs on the gzipped preview, for `/en/`, `/pt/` and `/es/` (`lighthouse/README.md`). Median runs:

| Run                                | Perf  | A11y | Best practices | SEO | LCP    | CLS     | TBT      |
| ---------------------------------- | ----- | ---- | -------------- | --- | ------ | ------- | -------- |
| Mobile, applied throttling (gated) | 98    | 100  | 100            | 100 | 1.57 s | ≤ 0.004 | 97–99 ms |
| Desktop (gated)                    | 99    | 100  | 100            | 100 | 0.84 s | 0       | 0 ms     |
| Mobile, simulated (reported)       | 84–85 | 100  | 100            | 100 | 4.28 s | 0       | ≤ 72 ms  |

- **The phone's CPU is calibrated** (since the first CI run): the slowdown is `benchmarkIndex / 500`, the Moto G4 of Lighthouse's throttling table, 8.2× on this Mac. With the default 4× the same build scored 98 here and 78 on GitHub's runner, because 4× emulates a different phone on each machine.
- **On CI the phone's Performance is a warning** (Gabriel, 2026-10-28). Even calibrated (4.8× there), GitHub's runner scores 88–89 with TBT 377–416 ms, against 97 ms here on the same commit: its scene tasks take 70–95 ms, hydration 223 ms and HTML parsing 212 ms. LCP, CLS, the other categories and desktop still fail the run; a low Performance or TBT shows as a warning annotation and under the summary table. Locally it stays a gate.
- **What phase 7 fixed on the way:**
  - Calibrated, the phone showed **TBT 460 ms and Performance 86**: when the GSAP runtime arrived, every scene mounted inside one React commit, a single 400 ms task (blocking the GSAP chunk took TBT to 90 ms). Scenes now mount one per task (`mountSoon` in `src/motion/runtime.ts`) and the triggers are measured once at the end: TBT 97–99 ms, Performance 98. The same work, no longer one block for a phone to sit through.
  - The fonts preloaded six files (about 565 KB), half of them the `latin-ext` subsets the page never used: every letter of PT, EN and ES is in `latin` (a unit test checks the content). Now three files, about 340 KB. Simulated mobile went from 78 to 85.
  - The site had no favicon, so every page logged a 404 (Best Practices 96 on desktop). It now has the reel mark as `icon.svg` and an Apple touch icon.
  - `pnpm preview` redirected every path outside `/Portfolio/` to the page, so Lighthouse read HTML as `/robots.txt` (SEO 92). It now answers 404 there, like Pages.
- **Why the simulated run is not the gate:** Lantern counts every request that starts before the observed LCP (61–127 ms here) as part of it, so the three preloaded fonts are charged to the hero line, although the line paints at once in the fallback font and swaps later. The applied run measures what a throttled phone shows, as `pnpm measure:vitals` does. Without the `opsz` axis the fonts would weigh about 160 KB and the simulated run would reach 91 (LCP still 3.4 s); the axis stays until Gabriel decides, since optical sizes are part of the type choice (COMMIT-SHEET §3).

## Tests added by the adjustment

- **5-second test:**
  - Viewports: 390 × 844, 768 × 1024, 1440 × 900, 1366 × 768 and 1280 × 720.
  - Elements: name, role, stack, "Remote", Download CV and Contact.
  - Each must be inside the viewport, and `elementFromPoint` at its center must return it or a child. This is checked before, during and after the peak, and in Quick view.
- **Intro:** the overlay is gone by 1.5 s; Skip and Esc work; it never runs with a hash, with reduced motion, in Quick view, or on a second load in the same session.
- **Quick view:**
  - Toggling it removes all ScrollTrigger instances and stops Lenis.
  - It persists across reloads and locales.
  - The page has no `[data-intro]` and no pin spacers.
  - The same headings and links exist in both modes.
- **Pin budget:** the sum of pin-spacer extra height is ≤ 1 × `innerHeight` at 1440 × 900.
- **Native scroll:** End, PageDown and anchor links reach their targets; a hash deep link lands on its section.
