-- Sistema Wave (Group Wave Enterprise) --
Uma plataforma interna usada por cerca de 100 pessoas para publicar campanhas na Meta em massa, editar e melhorar criativos com IA, gerar copies, gerenciar solicitações entre equipes (no estilo do ClickUp) e acompanhar dados de campanhas, financeiro e saúde da empresa em dashboards.

[mockup words] Campanhas · Solicitações · Relatórios · Dashboard · Todas as equipes · Esta semana · Nova solicitação · Solicitadas · Em andamento · Em revisão · Concluídas · Criação · Dados · Redação · Mídia · Seg · Ter · Qua · Qui · Sex · Hoje · Feito · Banners, 6 tamanhos · Auditoria de UTMs · Sequência de 3 e-mails · Corte de vídeo, 15 s · Título da landing page · Oferta, versão mobile · Relatório semanal · Pixel no novo domínio · Carrossel, 5 cards · Anúncios, 2ª rodada
Stack: Next.js, React, NestJS, TypeScript, PostgreSQL, Meta API, Prometheus, Grafana, Jenkins
[button] Detalhes técnicos
  O problema: Antes da plataforma, cada campanha era montada à mão no NewsBreak, no Meta Ads e no Taboola.
  Meu papel: O time divide o trabalho por áreas, e eu atuo em todas elas, para que cada parte se encaixe no sistema inteiro.
  Arquitetura:
    App web (Next.js, React) → API (NestJS)
    API (NestJS) → PostgreSQL
    API (NestJS) → API da Meta
  Decisões principais:
    - As campanhas sobem pela API da Meta, várias de uma vez. Antes, cada campanha era montada à mão em cada plataforma de anúncios.
    - Prometheus, Grafana e logs acompanham o sistema, e alertas vão para o Telegram em caso de erro ou quando uma rota está sobrecarregada. Para saber como o sistema está a qualquer momento, e ficar sabendo de erros e rotas sobrecarregadas assim que acontecem.
  Testes e deploy: Testes de segurança que simulam ataques reais, e testes de estresse que procuram erros e falhas que poderiam abrir uma brecha de segurança. O Jenkins roda os testes e as validações, e uma mudança só é aprovada se passar por eles. Ela vai primeiro para o ambiente de develop, onde testamos, e quando tudo está aprovado o tech lead faz o deploy.
  Resultado: Mais de 500 campanhas publicadas por dia pela API da Meta, por cerca de 100 pessoas dentro da empresa.

-- Campaign BI (Group Wave Enterprise) --
Um sistema interno de dados de campanhas, usado todos os dias pelos donos, pelo financeiro e pelos líderes de squad: resultados mensais e semanais e o desempenho de cada media buyer, atualizados a cada hora. Workers em NestJS processam os dados do RedTrack a partir de uma fila no RabbitMQ e gravam no PostgreSQL, e um app em Next.js com login Google os lê pela API em NestJS.
[image] Um gráfico de desempenho semanal com campanhas fictícias e media buyers inventados, no lugar do sistema interno.
[mockup words] Desempenho das campanhas · Mensal · Semanal · S · Receita · Investimento · Por media buyer · campanhas
Stack: Next.js, NestJS, PostgreSQL, RabbitMQ, n8n, RedTrack
[button] Detalhes técnicos
  O problema: O financeiro puxava os dados do RedTrack com um pequeno script em Python que gerava arquivos CSV. Cada extração levava de 45 minutos a 2 horas, conforme o período.
  Meu papel: Desenhei a arquitetura e construí o sistema inteiro, do começo ao fim.
  Arquitetura:
    RedTrack → n8n
    n8n → RabbitMQ
    RabbitMQ → NestJS (workers e API)
    App Next.js (login Google) → NestJS (workers e API)
    NestJS (workers e API) → PostgreSQL
  Decisões principais:
    - Visões mensais e semanais dos dados do RedTrack, e o desempenho de cada media buyer. Os donos, o financeiro e os líderes de squad analisam os dados todos os dias: o que está dando certo, o que está gastando e como está cada media buyer.
    - O n8n publica os dados do RedTrack numa fila no RabbitMQ, e vários workers em NestJS os processam em paralelo até o PostgreSQL. São muitos dados de uma vez. A fila separa a chegada dos dados do processamento: o n8n publica tudo no RabbitMQ, e os workers consomem no ritmo que o banco aguenta. Um registro que falha é tentado de novo sem afetar os outros, e se um worker cai nada se perde, porque a mensagem continua na fila. O RedTrack identifica cada registro, então uma mensagem processada duas vezes não duplica dados.
    - Um script de alocação pelo método dos maiores restos para conversões e receita. As métricas estavam infladas. O script corrigiu os números, e os resultados foram conferidos com as planilhas de referência.
  Testes e deploy: As verificações rodam no CI a cada mudança. Nada vai para o ar sem passar no CI, então um erro aparece no pipeline, e não depois de derrubar o sistema, mesmo que por pouco tempo.
  Resultado: Os dados do RedTrack agora se atualizam a cada hora durante o dia, e as cargas maiores rodam de madrugada. Os dashboards leem do PostgreSQL com consultas otimizadas, em vez de esperar de 45 minutos a 2 horas por um CSV. O Campaign BI hoje roda dentro do Sistema Wave.

-- Zibby --
Minha própria plataforma de e-commerce multiloja, lançada em outubro de 2026: vitrine, painel administrativo com cadastro de produtos e dashboards de vendas que mostram como cada produto está saindo, e pagamentos com Stripe. Cada integração é um provider, então cada loja pode ser criada e personalizada com as APIs de que precisa.
[image] Uma vitrine fictícia ao lado do seu painel administrativo.
[mockup words] Novidades · Casa · Cozinha · Carrinho (2) · Para o dia a dia · Caneca de cerâmica · Luminária de mesa · Bolsa de linho · Pedidos · Admin · Em separação · Pago · Despachado · Entregue
Stack: Next.js, NestJS, PostgreSQL, Prisma, Stripe, Resend, Microsoft Clarity, Meta Pixel
[button] Detalhes técnicos
  O problema: Gerenciar várias lojas online num só lugar, cada uma com seus próprios produtos, vendas e integrações.
  Meu papel: Produto próprio. Construí em fases com agentes de IA para programar, e cada fase seguiu plano → revisão → implementação → testes → revisão do diff → merge.
  Arquitetura:
    Vitrine (Next.js) → API (NestJS, monólito modular)
    Painel administrativo (Next.js) → API (NestJS, monólito modular)
    API (NestJS, monólito modular) → PostgreSQL (Prisma)
    API (NestJS, monólito modular) → Stripe (provider de pagamentos)
    API (NestJS, monólito modular) → Resend (provider de e-mail)
    Vitrine (Next.js) → Microsoft Clarity, Pixel da Meta
  Decisões principais:
    - Um monorepo pnpm com a API em NestJS e a vitrine e o painel em Next.js, organizado como monólito modular. Uma pessoa só constrói e opera, então tudo sai num deploy, com um banco e um lugar só para rastrear um erro. Microsserviços trariam chamadas de rede, deploys separados e falhas espalhadas entre serviços, sem ganho nesse tamanho. Cada área (lojas, produtos, pedidos, pagamentos) fica no próprio módulo, com fronteira clara, então uma delas pode virar um serviço separado se um dia precisar escalar. E no monorepo uma mudança que atravessa a API, a vitrine e o painel sai num único commit.
    - Microsoft Clarity na vitrine, e o Pixel da Meta configurado por loja. O Clarity grava as sessões e gera mapas de calor, então dá para ver onde os clientes clicam, até onde rolam a página e onde desistem. Cada loja coloca o próprio Pixel da Meta, que envia visitas, adições ao carrinho e compras de volta para a Meta, para medir e otimizar os anúncios dela.
    - Cada integração é um provider: Stripe para pagamentos e o Resend para e-mail são os primeiros, e outras APIs se conectam do mesmo jeito. Para que cada loja possa ser criada e personalizada como precisar, com os serviços que escolher.
  Testes e deploy: Testes automatizados em todo o monorepo; cada fase passou por eles antes da revisão do diff. Deploy em uma VPS, com backups de emergência. Os dados dos clientes e as chaves de API ficam criptografados: mesmo numa invasão, só podem ser lidos com a chave de descriptografia.
  Resultado: Lançada em outubro de 2026.

-- Hostly (IA Robots Solutions) --
Uma plataforma multiempresa para robôs de atendimento OrionStar: um app Android próprio substitui o de fábrica e toca as campanhas, músicas e falas agendadas num painel web. Os anúncios também vão para telões de LED cadastrados, inclusive em eventos.
[image] Uma tela de agenda do robô com uma playlist de campanhas fictícia, no lugar do sistema real.
[mockup words] Hoje · Campanha · Música · Boas-vindas · Lobby, trilha A · Oferta semanal · Menu do almoço · Lobby, trilha B · Tocando agora · Campanha, 30 segundos · A seguir · Luz da manhã · Portas abertas · Hora calma · Segundo andar · Check-in tardio
Stack: Kotlin, RobotOS, NestJS, Next.js, PostgreSQL, Redis, BullMQ, FFmpeg, Docker
[button] Detalhes técnicos
  O problema: O app de fábrica do robô dificultava trocar a mídia, não deixava agendar campanhas, falhava na tela grande e não gerava relatório.
  Meu papel: Escrevi a especificação e desenvolvo o sistema inteiro, com agentes de IA trabalhando em paralelo, um por issue: a API, o painel, o worker de mídia e o app Android do robô.
  Arquitetura:
    Painel (Next.js) → API (NestJS)
    App do robô (Kotlin) → API (NestJS) (WebSocket)
    App do robô (Kotlin) → RobotOS no LuckiBot Plus (RobotGateway)
    API (NestJS) → Worker de mídia (FFmpeg) (fila)
    API (NestJS) → PostgreSQL
    API (NestJS) → Telão de LED cadastrado (anúncios)
    Worker de mídia (FFmpeg) → Storage S3
  Decisões principais:
    - O app do robô acessa o RobotOS por uma camada própria, o RobotGateway, que também tem uma versão falsa para o emulador. O app roda e é testado sem o robô de verdade, e se a OrionStar liberar o AgentOS para o LuckiBot Plus, só essa camada muda.
    - A nuvem decide e o robô executa: cada mudança no painel recompila um manifesto versionado, e o robô segue o último que recebeu. Sem internet, o robô continua seguindo a agenda, toca a mídia do cache e guarda os eventos para mandar quando a rede voltar.
    - Multiempresa desde o início: operadora, clientes, locais e robôs, com papéis e marca por cliente, que o robô herda do cliente ou da operadora. Cada cliente, como um shopping, usa o painel com a própria marca e vê só os próprios robôs e campanhas. O escopo por organização é aplicado no centro da API e no banco, e não rota por rota, então a mesma base pode virar um SaaS.
  Testes e deploy: Testes de unidade e e2e na API, no painel e no worker, testes de contrato do RobotGateway e as verificações do app Android, tudo no CI a cada mudança. A API nega por padrão, com uma varredura que falha se alguma rota ficar sem guarda; o login tem autenticação em dois fatores, e a auditoria é uma cadeia assinada com HMAC. API, painel, worker, PostgreSQL e Redis rodam com Docker Compose numa VPS, atrás de HTTPS automático. A mídia fica num storage S3 privado, servida só por URL assinada; o deploy só passa por VPN, e um backup diário criptografado sai do servidor.
  Resultado: Em uso: conecta ao robô e aos telões de LED cadastrados e transmite anúncios nos dois, inclusive em eventos.
