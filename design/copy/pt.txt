-- Sistema Wave (Group Wave Enterprise) --
Uma plataforma interna para publicar campanhas na Meta em massa, editar e melhorar criativos com IA, gerar copies, gerenciar solicitações entre equipes (no estilo do ClickUp) e acompanhar dados de campanhas, financeiro e saúde da empresa em dashboards.

Stack: Next.js, React, NestJS, TypeScript, PostgreSQL, Meta API, Prometheus, Grafana, Jenkins
[button] Detalhes técnicos
  O problema: Antes da plataforma, cada campanha era montada à mão no NewsBreak, no Meta Ads e no Taboola.
  Meu papel: Dividimos o trabalho por partes, mas mexi em todas elas, para que cada peça se encaixe no sistema inteiro.
  Arquitetura:
    App web (Next.js, React) → API (NestJS)
    API (NestJS) → PostgreSQL
    API (NestJS) → API da Meta
  Decisões principais:
    - Prometheus, Grafana e logs acompanham o sistema, e alertas vão para o Telegram em caso de erro ou quando uma rota está sobrecarregada. Para saber como o sistema está a qualquer momento, e ficar sabendo de erros e rotas sobrecarregadas assim que acontecem.
    - As campanhas sobem pela API da Meta, várias de uma vez. Antes, cada campanha era montada à mão em cada plataforma de anúncios.
  Testes e deploy: Testes de segurança que simulam ataques reais, e testes de estresse que procuram erros e falhas que poderiam abrir uma brecha de segurança. O Jenkins roda os testes e as validações, e uma mudança só é aprovada se passar por eles. Ela vai primeiro para o ambiente de develop, onde testamos, e quando tudo está aprovado o tech lead faz o deploy.
  Resultado: Mais de 1.000 campanhas publicadas por dia pela API da Meta, por cerca de 100 pessoas dentro da empresa.

-- Campaign BI (Group Wave Enterprise) --
Um sistema interno para dados de campanhas: workers em NestJS processam os dados do RedTrack a partir de uma fila no RabbitMQ e gravam no PostgreSQL, e um app em Next.js com login Google os lê pela API em NestJS: resultados mensais e semanais, e o desempenho de cada media buyer.
[image] Um gráfico de desempenho semanal com campanhas fictícias e media buyers inventados, no lugar do sistema interno.
[mockup words] Desempenho das campanhas · Mensal · Semanal · S · Receita · Investimento · Por media buyer · campanhas
Stack: Next.js, NestJS, PostgreSQL, RabbitMQ, n8n, RedTrack
[button] Detalhes técnicos
  O problema: O financeiro puxava os dados do RedTrack com um pequeno script em Python que gerava arquivos CSV. Cada extração levava de 45 minutos a 2 horas, conforme o período.
  Meu papel: Desenhei a arquitetura e construí o sistema inteiro, do começo ao fim.
  Arquitetura:
    RedTrack → n8n
    n8n → RabbitMQ
    RabbitMQ → NestJS (workers e API)
    App Next.js (login Google) → NestJS (workers e API)
    NestJS (workers e API) → PostgreSQL
  Decisões principais:
    - Visões mensais e semanais dos dados do RedTrack, e o desempenho de cada media buyer. Os donos, o financeiro e os líderes de squad analisam os dados todos os dias: o que está dando certo, o que está gastando e como está cada media buyer.
    - O n8n leva os dados do RedTrack para uma fila no RabbitMQ, e workers em NestJS os processam até o PostgreSQL. São muitos dados para cadastrar, e um erro não pode fazer perder tudo. Com a fila, um registro que falha não afeta os outros.
    - Um script de alocação pelo método dos maiores restos para conversões e receita. As métricas estavam infladas. O script corrigiu os números, e os resultados foram conferidos com as planilhas de referência.
  Testes e deploy: As verificações rodam no CI a cada mudança. Nada vai para o ar sem passar no CI, então um erro é pego antes de derrubar o sistema, mesmo que por pouco tempo, em vez de ser caçado depois.
  Resultado: Os dados do RedTrack agora se atualizam a cada hora durante o dia, e as cargas maiores rodam de madrugada. Os dashboards leem do PostgreSQL com consultas otimizadas, em vez de esperar de 45 minutos a 2 horas por um CSV. O Campaign BI hoje roda dentro do Sistema Wave.
  Sistema interno, sem link público
