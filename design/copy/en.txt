-- Campaign BI (Group Wave Enterprise) --
An internal campaign-data system used every day by the owners, finance and the squad leads: monthly and weekly results and each media buyer's performance, refreshed every hour. NestJS workers process RedTrack data from a RabbitMQ queue into PostgreSQL, and a Next.js app with Google sign-in reads it through the NestJS API.
[image] A weekly performance chart with fictional campaigns and invented media buyers, standing in for the internal system.
[mockup words] Campaign performance · Monthly · Weekly · W · Revenue · Spend · By media buyer · campaigns
Stack: Next.js, NestJS, PostgreSQL, RabbitMQ, n8n, RedTrack
[button] Technical details
  The problem: Finance pulled RedTrack data with a small Python script that wrote CSV files. Each pull took 45 minutes to 2 hours, depending on the date range.
  My role: I designed the architecture and built the whole system, end to end.
  Architecture:
    RedTrack → n8n
    n8n → RabbitMQ
    RabbitMQ → NestJS (workers, API)
    Next.js app (Google sign-in) → NestJS (workers, API)
    NestJS (workers, API) → PostgreSQL
  Key decisions:
    - Monthly and weekly views of RedTrack data, and each media buyer's performance. The owners, finance and the squad leads review the data every day: what is working, what is spending, and how each media buyer is doing.
    - n8n publishes RedTrack data to a RabbitMQ queue, and several NestJS workers process it in parallel into PostgreSQL. There is a lot of data at once. The queue separates bringing the data in from processing it: n8n publishes everything to RabbitMQ, and the workers consume it at the pace the database can take. A record that fails is retried without affecting the others, and if a worker goes down nothing is lost, because the message stays in the queue. RedTrack identifies each record, so a message processed twice never duplicates data.
    - A largest-remainder allocation script for conversions and revenue. The metrics were inflated. The script corrected them, and the results were reconciled against the reference spreadsheets.
  Testing and deploy: The checks run in CI on every change. Nothing ships until CI passes, so an error shows up in the pipeline, not after it has taken the system down, even briefly.
  Outcome: RedTrack data now refreshes every hour during the day, and the larger loads run overnight. The dashboards read it from PostgreSQL through optimized queries instead of waiting 45 minutes to 2 hours for a CSV. Campaign BI now runs inside Sistema Wave.
  Internal system, no public link

-- Zibby --
My own multi-store e-commerce platform, launched in October 2026: a storefront, an admin panel with product registration and sales dashboards that show how each product is selling, and Stripe payments. Every integration is a provider, so each store can be created and customized with the APIs it needs.
[image] A fictional storefront next to its admin panel.
[mockup words] New · Home · Kitchen · Cart (2) · Made for every day · Ceramic mug · Desk lamp · Linen tote · Orders · Admin · Preparing · Paid · Shipped · Delivered
Stack: Next.js, NestJS, PostgreSQL, Prisma, Stripe, Resend, Microsoft Clarity, Meta Pixel
[button] Technical details
  The problem: Running several online stores from one place, each with its own products, sales and integrations.
  My role: My own product. I built it in phases with AI coding agents, and every phase went plan → review → implement → tests → diff review → merge.
  Architecture:
    Storefront (Next.js) → API (NestJS, modular monolith)
    Admin panel (Next.js) → API (NestJS, modular monolith)
    API (NestJS, modular monolith) → PostgreSQL (Prisma)
    API (NestJS, modular monolith) → Stripe (payments provider)
    API (NestJS, modular monolith) → Resend (e-mail provider)
    Storefront (Next.js) → Microsoft Clarity and Meta Pixel
  Key decisions:
    - A pnpm monorepo with the NestJS API and the Next.js storefront and admin, organized as a modular monolith. One person builds and runs it, so it ships as one deploy with one database and one place to trace an error. Microservices would add network calls, separate deploys and failures spread across services, with nothing to gain at this size. Each area (stores, products, orders, payments) stays in its own module with a clear boundary, so one can become a separate service if it ever needs to scale. And in the monorepo, a change that crosses the API, the storefront and the admin goes out in one commit.
    - Microsoft Clarity in the storefront, and a Meta Pixel set per store. Clarity records sessions and builds heatmaps, so I can see where customers click, how far they scroll and where they give up. Each store adds its own Meta Pixel, which reports visits, add-to-carts and purchases back to Meta, so its ads can be measured and optimized.
    - Every integration is a provider: Stripe for payments and Resend for e-mail are the first, and other APIs plug in the same way. So each store can be created and customized however it needs, with the services it chooses.
  Testing and deploy: Automated tests across the monorepo; each phase passed them before its diff review. Deployed to a VPS, with emergency backups. Customer data and API keys are encrypted, so even after a break-in they can only be read with the decryption key.
  Outcome: Launched in October 2026.

-- Hostly (IA Robots Solutions) --
A multi-company platform for OrionStar service robots: its own Android app replaces the factory one and plays the campaigns, music and spoken lines scheduled on a web panel. The ads also go to registered LED screens, at events too.
[image] A robot schedule screen with a fictional campaign playlist, standing in for the real system.
[mockup words] Today · Campaign · Music · Welcome message · Lobby set A · Spring offer · Lunch menu · Lobby set B · Now playing · Campaign, 30 seconds · Up next · Morning light · Open doors · Quiet hour · Second floor · Late check-in
Stack: Kotlin, RobotOS, NestJS, Next.js, PostgreSQL, Redis, BullMQ, FFmpeg, Docker
[button] Technical details
  The problem: The robot's factory app made it hard to change the media, could not schedule campaigns, failed on the big screen and kept no report.
  My role: I wrote the specification and build the whole system, with AI coding agents working in parallel, one per issue: the API, the panel, the media worker and the Android app on the robot.
  Architecture:
    Panel (Next.js) → API (NestJS)
    Robot app (Kotlin) → API (NestJS) (WebSocket)
    Robot app (Kotlin) → RobotOS on LuckiBot Plus (RobotGateway)
    API (NestJS) → Media worker (FFmpeg) (queue)
    API (NestJS) → PostgreSQL
    API (NestJS) → Registered LED screen (ads)
    Media worker (FFmpeg) → S3 storage
  Key decisions:
    - The robot app reaches RobotOS through its own layer, the RobotGateway, which also has a fake for the emulator. The app runs and is tested without the real robot, and if OrionStar ever ships AgentOS for the LuckiBot Plus, only that layer changes.
    - The cloud decides and the robot executes: every change on the panel recompiles a versioned manifest, and the robot follows the last one it received. Without internet, the robot keeps to its schedule, plays the media from its cache and stores its events to send once the network is back.
    - Multi-company from the start: operator, clients, sites and robots, with roles and a brand per client that a robot inherits from its client or the operator. Each client, such as a shopping mall, uses the panel under its own brand and sees only its own robots and campaigns. The organization scope is enforced at the center of the API and in the database, not route by route, so the same base can become a SaaS.
  Testing and deploy: Unit and end-to-end tests on the API, the panel and the worker, contract tests for the RobotGateway and the Android build checks, all in CI on every change. The API denies by default, with a sweep that fails if any route has no guard; login has two-factor authentication, and the audit log is a chain signed with HMAC. The API, panel, worker, PostgreSQL and Redis run with Docker Compose on a VPS behind automatic HTTPS. Media sits in private S3 storage, served only through signed URLs; deploys go only through a VPN, and a daily encrypted backup leaves the server.
  Outcome: In use: it connects to the robot and to registered LED screens and streams ads to both, at events too.
  Internal system, no public link
