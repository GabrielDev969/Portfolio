-- Campaign BI (Group Wave Enterprise) --
An internal campaign-data system used every day by the owners, finance and the squad leads: monthly and weekly results and each media buyer's performance, refreshed every hour. NestJS workers process RedTrack data from a RabbitMQ queue into PostgreSQL, and a Next.js app with Google sign-in reads it through the NestJS API.
[image] A weekly performance chart with fictional campaigns and invented media buyers, standing in for the internal system.
[mockup words] Campaign performance · Monthly · Weekly · W · Revenue · Spend · By media buyer · campaigns
Stack: Next.js, NestJS, PostgreSQL, RabbitMQ, n8n, RedTrack
[button] Technical details
  The problem: Finance pulled RedTrack data with a small Python script that wrote CSV files. Each pull took 45 minutes to 2 hours, depending on the date range.
  My role: I designed the architecture and built the whole system, end to end.
  Architecture:
    RedTrack → n8n
    n8n → RabbitMQ
    RabbitMQ → NestJS (workers, API)
    Next.js app (Google sign-in) → NestJS (workers, API)
    NestJS (workers, API) → PostgreSQL
  Key decisions:
    - Monthly and weekly views of RedTrack data, and each media buyer's performance. The owners, finance and the squad leads review the data every day: what is working, what is spending, and how each media buyer is doing.
    - n8n publishes RedTrack data to a RabbitMQ queue, and several NestJS workers process it in parallel into PostgreSQL. There is a lot of data at once. The queue separates bringing the data in from processing it: n8n publishes everything to RabbitMQ, and the workers consume it at the pace the database can take. A record that fails is retried without affecting the others, and if a worker goes down nothing is lost, because the message stays in the queue. RedTrack identifies each record, so a message processed twice never duplicates data.
    - A largest-remainder allocation script for conversions and revenue. The metrics were inflated. The script corrected them, and the results were reconciled against the reference spreadsheets.
  Testing and deploy: The checks run in CI on every change. Nothing ships until CI passes, so an error shows up in the pipeline, not after it has taken the system down, even briefly.
  Outcome: RedTrack data now refreshes every hour during the day, and the larger loads run overnight. The dashboards read it from PostgreSQL through optimized queries instead of waiting 45 minutes to 2 hours for a CSV. Campaign BI now runs inside Sistema Wave.
  Internal system, no public link
