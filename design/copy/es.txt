-- Sistema Wave (Group Wave Enterprise) --
Una plataforma interna que usan unas 100 personas para publicar campañas en Meta de forma masiva, editar y mejorar creatividades con IA, generar copies, gestionar solicitudes entre equipos (al estilo de ClickUp) y seguir datos de campañas, finanzas y salud de la empresa en dashboards.

Stack: Next.js, React, NestJS, TypeScript, PostgreSQL, Meta API, Prometheus, Grafana, Jenkins
[button] Detalles técnicos
  El problema: Antes de la plataforma, cada campaña se armaba a mano en NewsBreak, Meta Ads y Taboola.
  Mi rol: El equipo divide el trabajo por áreas, y yo trabajo en todas ellas, para que cada parte encaje en el sistema completo.
  Arquitectura:
    App web (Next.js, React) → API (NestJS)
    API (NestJS) → PostgreSQL
    API (NestJS) → API de Meta
  Decisiones clave:
    - Las campañas se publican a través de la API de Meta, varias a la vez. Antes, cada campaña se armaba a mano en cada plataforma de anuncios.
    - Prometheus, Grafana y logs vigilan el sistema, y las alertas llegan a Telegram ante errores o cuando una ruta está sobrecargada. Para saber cómo está el sistema en todo momento, y enterarse de errores y rutas sobrecargadas en cuanto ocurren.
  Pruebas y despliegue: Pruebas de seguridad que simulan ataques reales, y pruebas de estrés que buscan errores y fallas que podrían abrir una brecha de seguridad. Jenkins ejecuta las pruebas y validaciones, y un cambio solo se aprueba si las pasa. Primero va al entorno de develop, donde lo probamos, y cuando todo está aprobado el tech lead hace el deploy.
  Resultado: Más de 500 campañas publicadas al día a través de la API de Meta, por unas 100 personas dentro de la empresa.

-- Campaign BI (Group Wave Enterprise) --
Un sistema interno de datos de campañas, que usan todos los días los dueños, finanzas y los líderes de squad: resultados mensuales y semanales y el rendimiento de cada media buyer, actualizados cada hora. Workers en NestJS procesan los datos de RedTrack desde una cola en RabbitMQ y los guardan en PostgreSQL, y una app en Next.js con inicio de sesión de Google los consulta a través de la API en NestJS.
[image] Un gráfico de rendimiento semanal con campañas ficticias y media buyers inventados, en lugar del sistema interno.
[mockup words] Rendimiento de campañas · Mensual · Semanal · S · Ingresos · Inversión · Por media buyer · campañas
Stack: Next.js, NestJS, PostgreSQL, RabbitMQ, n8n, RedTrack
[button] Detalles técnicos
  El problema: Finanzas extraía los datos de RedTrack con un pequeño script en Python que generaba archivos CSV. Cada extracción tardaba de 45 minutos a 2 horas, según el período.
  Mi rol: Diseñé la arquitectura y construí todo el sistema, de punta a punta.
  Arquitectura:
    RedTrack → n8n
    n8n → RabbitMQ
    RabbitMQ → NestJS (workers y API)
    App Next.js (inicio de sesión de Google) → NestJS (workers y API)
    NestJS (workers y API) → PostgreSQL
  Decisiones clave:
    - Vistas mensuales y semanales de los datos de RedTrack, y el rendimiento de cada media buyer. Los dueños, finanzas y los líderes de squad analizan los datos todos los días: qué está funcionando, qué está gastando y cómo va cada media buyer.
    - n8n publica los datos de RedTrack en una cola de RabbitMQ, y varios workers en NestJS los procesan en paralelo hasta PostgreSQL. Son muchos datos a la vez. La cola separa la llegada de los datos de su procesamiento: n8n publica todo en RabbitMQ, y los workers lo consumen al ritmo que la base de datos soporta. Un registro que falla se reintenta sin afectar a los demás, y si un worker se cae no se pierde nada, porque el mensaje sigue en la cola. RedTrack identifica cada registro, así que un mensaje procesado más de una vez no duplica datos.
    - Un script de asignación por el método de los restos mayores para conversiones e ingresos. Las métricas estaban infladas. El script corrigió los números, y los resultados se conciliaron con las planillas de referencia.
  Pruebas y despliegue: Las verificaciones se ejecutan en CI con cada cambio. Nada se publica sin pasar el CI, así que un error aparece en el pipeline, y no después de tumbar el sistema, aunque sea por poco tiempo.
  Resultado: Los datos de RedTrack ahora se actualizan cada hora durante el día, y las cargas más grandes corren de madrugada. Los dashboards los leen de PostgreSQL con consultas optimizadas, en lugar de esperar de 45 minutos a 2 horas por un CSV. Campaign BI hoy funciona dentro de Sistema Wave.
  Sistema interno, sin enlace público

-- Zibby --
Mi propia plataforma de e-commerce multitienda, lanzada en octubre de 2026: tienda online, panel de administración con registro de productos y dashboards de ventas que muestran cómo se vende cada producto, y pagos con Stripe. Cada integración es un provider, así que cada tienda puede crearse y personalizarse con las APIs que necesite.
[image] Una tienda ficticia junto a su panel de administración.
[mockup words] Novedades · Hogar · Cocina · Carrito (2) · Para cada día · Taza de cerámica · Lámpara de mesa · Bolso de lino · Pedidos · Admin · En preparación · Pagado · Despachado · Entregado
Stack: Next.js, NestJS, PostgreSQL, Prisma, Stripe, Resend, Microsoft Clarity, Meta Pixel
[button] Detalles técnicos
  El problema: Gestionar varias tiendas online desde un solo lugar, cada una con sus propios productos, ventas e integraciones.
  Mi rol: Producto propio. Lo construí por fases con agentes de IA para programar, y cada fase siguió plan → revisión → implementación → pruebas → revisión del diff → merge.
  Arquitectura:
    Tienda (Next.js) → API (NestJS, monolito modular)
    Panel de administración (Next.js) → API (NestJS, monolito modular)
    API (NestJS, monolito modular) → PostgreSQL (Prisma)
    API (NestJS, monolito modular) → Stripe (provider de pagos)
    API (NestJS, monolito modular) → Resend (provider de e-mail)
    Tienda (Next.js) → Microsoft Clarity, Píxel de Meta
  Decisiones clave:
    - Un monorepo pnpm con la API en NestJS y la tienda y el panel en Next.js, organizado como monolito modular. Una sola persona lo construye y lo opera, así que todo sale en un deploy, con una base de datos y un solo lugar para rastrear un error. Los microservicios sumarían llamadas de red, deploys separados y fallas repartidas entre servicios, sin ganancia a este tamaño. Cada área (tiendas, productos, pedidos, pagos) queda en su propio módulo, con una frontera clara, así que una de ellas puede convertirse en un servicio aparte si algún día necesita escalar. Y en el monorepo, un cambio que cruza la API, la tienda y el panel sale en un solo commit.
    - Microsoft Clarity en la tienda, y el Píxel de Meta configurado por tienda. Clarity graba las sesiones y genera mapas de calor, así que se puede ver dónde hacen clic los clientes, hasta dónde bajan en la página y dónde abandonan. Cada tienda agrega su propio Píxel de Meta, que envía visitas, productos agregados al carrito y compras de vuelta a Meta, para medir y optimizar sus anuncios.
    - Cada integración es un provider: Stripe para pagos y Resend para e-mail son los primeros, y otras APIs se conectan de la misma forma. Para que cada tienda pueda crearse y personalizarse como necesite, con los servicios que elija.
  Pruebas y despliegue: Pruebas automatizadas en todo el monorepo; cada fase las pasó antes de la revisión del diff. Desplegado en un VPS, con copias de seguridad de emergencia. Los datos de los clientes y las claves de API están cifrados: incluso ante una intrusión, solo pueden leerse con la clave de descifrado.
  Resultado: Lanzada en octubre de 2026.

-- Hostly (IA Robots Solutions) --
Una plataforma multiempresa para robots de servicio OrionStar: una app Android propia reemplaza la de fábrica y reproduce las campañas, la música y los mensajes de voz programados en un panel web. Los anuncios también van a pantallas LED registradas, también en eventos.
[image] Una pantalla de programación del robot con una playlist de campañas ficticia, en lugar del sistema real.
[mockup words] Hoy · Campaña · Música · Bienvenida · Lobby, lista A · Oferta semanal · Menú de almuerzo · Lobby, lista B · Reproduciendo · Campaña, 30 segundos · A continuación · Luz de mañana · Puertas abiertas · Hora tranquila · Segundo piso · Check-in tardío
Stack: Kotlin, RobotOS, NestJS, Next.js, PostgreSQL, Redis, BullMQ, FFmpeg, Docker
[button] Detalles técnicos
  El problema: La app de fábrica del robot hacía difícil cambiar los contenidos, no permitía programar campañas, fallaba en la pantalla grande y no generaba informes.
  Mi rol: Escribí la especificación y desarrollo todo el sistema, con agentes de IA trabajando en paralelo, uno por issue: la API, el panel, el worker de contenidos y la app Android del robot.
  Arquitectura:
    Panel (Next.js) → API (NestJS)
    App del robot (Kotlin) → API (NestJS) (WebSocket)
    App del robot (Kotlin) → RobotOS en LuckiBot Plus (RobotGateway)
    API (NestJS) → Worker de contenidos (FFmpeg) (cola)
    API (NestJS) → PostgreSQL
    API (NestJS) → Pantalla LED registrada (anuncios)
    Worker de contenidos (FFmpeg) → Almacenamiento S3
  Decisiones clave:
    - La app del robot accede a RobotOS a través de una capa propia, el RobotGateway, que también tiene una versión falsa para el emulador. La app funciona y se prueba sin el robot real, y si OrionStar libera AgentOS para el LuckiBot Plus, solo cambia esa capa.
    - La nube decide y el robot ejecuta: cada cambio en el panel recompila un manifiesto versionado, y el robot sigue el último que recibió. Sin internet, el robot sigue su agenda, reproduce los contenidos de la caché y guarda los eventos para enviarlos cuando vuelva la red.
    - Multiempresa desde el inicio: operadora, clientes, sitios y robots, con roles y una marca por cliente que el robot hereda del cliente o de la operadora. Cada cliente, como un centro comercial, usa el panel con su propia marca y ve solo sus propios robots y campañas. El alcance por organización se aplica en el centro de la API y en la base de datos, y no ruta por ruta, así que la misma base puede convertirse en un SaaS.
  Pruebas y despliegue: Pruebas unitarias y de punta a punta en la API, el panel y el worker, pruebas de contrato del RobotGateway y las verificaciones de la app Android, todo en CI con cada cambio. La API niega por defecto, con un barrido que falla si alguna ruta queda sin guarda; el inicio de sesión tiene autenticación de doble factor, y la auditoría es una cadena firmada con HMAC. La API, el panel, el worker, PostgreSQL y Redis corren con Docker Compose en un VPS, detrás de HTTPS automático. Los contenidos están en un almacenamiento S3 privado, servidos solo con URL firmadas; el deploy solo pasa por VPN, y una copia de seguridad diaria cifrada sale del servidor.
  Resultado: En uso: se conecta al robot y a las pantallas LED registradas y transmite anuncios en ambos, también en eventos.
